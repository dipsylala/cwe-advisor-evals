## Verdict

Exploitable. The code uses `Cipher.getInstance("AES")` without specifying a mode or padding, which defaults to ECB (Electronic CodeBook) mode. ECB encrypts each plaintext block independently, producing identical ciphertext for identical plaintext blocks. This leaks patterns in the plaintext SSN data.

## Source

User-controlled input: `request.getParameter("ssn")` on line 13, passed to encryption on line 23.

## Fix

**Vulnerable code (line 21-23):**
```java
Cipher cipher = Cipher.getInstance("AES");
cipher.init(Cipher.ENCRYPT_MODE, key);
byte[] ciphertext = cipher.doFinal(ssn.getBytes("UTF-8"));
```

**Fixed code:**
```java
SecureRandom random = new SecureRandom();
byte[] iv = new byte[12];
random.nextBytes(iv);

Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
GCMParameterSpec spec = new GCMParameterSpec(128, iv);
cipher.init(Cipher.ENCRYPT_MODE, key, spec);
byte[] ciphertext = cipher.doFinal(ssn.getBytes("UTF-8"));

// Prepend IV to ciphertext for decryption
byte[] result = new byte[iv.length + ciphertext.length];
System.arraycopy(iv, 0, result, 0, iv.length);
System.arraycopy(ciphertext, 0, result, iv.length, ciphertext.length);
```

Required imports:
```java
import javax.crypto.spec.GCMParameterSpec;
import java.security.SecureRandom;
```

## Explanation

The fix replaces ECB with AES/GCM (Galois/Counter Mode), which is an authenticated encryption mode that prevents pattern leakage. Each message receives a fresh 12-byte IV generated by `SecureRandom`, which is passed to `GCMParameterSpec(128, iv)` to specify a 128-bit authentication tag. The cipher is initialized with both the key and the GCM parameter specification. The IV is prepended to the ciphertext so the decryption side can extract and use it. This eliminates the pattern-leakage vulnerability while adding authentication to detect tampering. GCM does not use padding (`NoPadding`), and the authentication tag is automatically appended by the cipher during encryption.

## Behaviour changes

- IV generation and storage: The fix generates a fresh 12-byte IV for each encryption and prepends it to the ciphertext, increasing output size by 12 bytes. Decryption must extract the leading 12 bytes as the IV before decrypting. Reason: AES/GCM requires a unique IV per message to be secure; ECB has no IV at all.
- Initialization with `GCMParameterSpec`: The `cipher.init()` call now requires a third parameter (the spec), where the original omitted it. Reason: GCM mode requires explicit IV specification via `GCMParameterSpec`.
- Authentication tag: GCM appends a 16-byte authentication tag to the ciphertext, increasing output by 16 bytes beyond the plaintext and IV. The original plaintext is no longer recoverable if the tag is tampered with. Reason: GCM provides authenticated encryption; ECB provides only confidentiality.
- No padding: GCM requires `NoPadding` because the mode does not use block padding. The original transformation defaulted to PKCS5Padding. Reason: GCM is a stream-based authenticated encryption mode.
- `SecureRandom` dependency: The code now requires generating cryptographic randomness for the IV, which is not an extra dependency (SecureRandom is in java.security). Reason: Each encryption must use a unique IV.
