## Verdict
The code constructs HTML by concatenating unsanitized CGI parameter values directly into a string, then outputs that string. User-controlled data from `$ticket_subject` and `$customer_reply` are inserted into HTML context without entity encoding, allowing arbitrary JavaScript execution in the browser.

## Source
Lines 12-13 obtain untrusted user input from CGI parameters:
```
my $ticket_subject = $cgi->param('subject');
my $customer_reply = $cgi->param('reply');
```

Lines 21-22 embed these values directly into HTML markup without escaping:
```
. "<h2>" . $ticket_subject . "</h2>"
. "<div class='reply'>" . $customer_reply . "</div>"
```

Line 27 outputs the constructed HTML to the response.

## Fix
Use CGI's `escapeHTML()` function to encode special HTML characters in user-supplied values before inserting them into the markup:

```perl
my $ticket_html = "<div class='ticket'>"
    . "<h2>" . $cgi->escapeHTML($ticket_subject) . "</h2>"
    . "<div class='reply'>" . $cgi->escapeHTML($customer_reply) . "</div>"
    . $status_badge
    . "</div>";
```

The `$cgi->escapeHTML()` method encodes `<`, `>`, `&`, and `"` characters as HTML entities (`&lt;`, `&gt;`, `&amp;`, `&quot;`), preventing the browser from interpreting user input as markup or JavaScript.

## Explanation
XSS vulnerabilities arise when untrusted input is inserted into HTML output without encoding. The CGI module's `escapeHTML()` function provides the necessary sanitization by converting HTML metacharacters to their entity equivalents. This ensures that user input is treated as data content rather than executable code, regardless of what characters or scripts an attacker includes. The `$status_badge` from `build_status_badge()` can remain unescaped because it is generated by the application code itself, not derived from user input.
