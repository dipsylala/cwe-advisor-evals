## Verdict

exploitable

## Source

The session ID token is generated from an attacker-controlled context (user login) and must be unpredictable. The sink is `math/rand.Intn()` on line 18, which draws from a general-purpose PRNG rather than a cryptographic generator. An attacker can predict future session IDs by observing the PRNG output or its seed, enabling session hijacking.

## Fix

**Vulnerable Code:**
```go
import (
	"fmt"
	"math/rand"
	"net/http"
)

// LoginHandler issues a session cookie after a successful login.
func LoginHandler(w http.ResponseWriter, r *http.Request) {
	username := r.FormValue("username")
	if username == "" {
		http.Error(w, "username required", http.StatusBadRequest)
		return
	}

	// SAST FINDING: CWE-330 (Use of Insufficiently Random Values) reported here. Sink is the next statement.
	token := rand.Intn(1000000000)
	sessionID := fmt.Sprintf("%s-%d", username, token)
	
	http.SetCookie(w, &http.Cookie{
		Name:     "session_id",
		Value:    sessionID,
		HttpOnly: true,
		Path:     "/",
	})

	fmt.Fprintf(w, "welcome %s", username)
}
```

**Fixed Code:**
```go
import (
	"crypto/rand"
	"encoding/base64"
	"fmt"
	"net/http"
)

// LoginHandler issues a session cookie after a successful login.
func LoginHandler(w http.ResponseWriter, r *http.Request) {
	username := r.FormValue("username")
	if username == "" {
		http.Error(w, "username required", http.StatusBadRequest)
		return
	}

	// Fixed: Use crypto/rand for cryptographically secure random token
	b := make([]byte, 16)
	if _, err := rand.Read(b); err != nil {
		http.Error(w, "Internal error", http.StatusInternalServerError)
		return
	}
	token := base64.RawURLEncoding.EncodeToString(b)
	sessionID := fmt.Sprintf("%s-%s", username, token)

	http.SetCookie(w, &http.Cookie{
		Name:     "session_id",
		Value:    sessionID,
		HttpOnly: true,
		Path:     "/",
	})

	fmt.Fprintf(w, "welcome %s", username)
}
```

## Explanation

The original code uses `math/rand.Intn()` to generate a session token, which is drawn from Go's general-purpose PRNG. This generator is not cryptographically secure and produces output that is easily predictable, even when seeded. The fix replaces this with `crypto/rand.Read()`, which draws from the operating system's cryptographic random source. The generated bytes are then encoded using `base64.RawURLEncoding`, which safely encodes binary data into a URL-safe string. This provides at least 128 bits of cryptographic entropy (16 bytes = 128 bits), meeting OWASP ASVS requirements for non-guessable values. The error handling ensures the application fails safely if random generation fails. The sessionID format changes from a numeric token to a base64-encoded string, but maintains the same semantic purpose and is suitable for use in HTTP cookies.

## Behaviour changes

1. **Session ID format changes**: The sessionID format changes from `{username}-{integer}` (e.g., `user-123456789`) to `{username}-{base64string}` (e.g., `user-A1b2C3d4E5f6G7h8I9j0Kl_mN-oPq`). This is a breaking change for any code that parses the session ID format, but the new format is still suitable for cookie values and provides superior security.

2. **Error handling added**: The original code had no error path; the fixed code adds error handling for `crypto/rand.Read()` failures, returning HTTP 500 if random generation fails. This prevents silent security failures.

3. **Import changes**: `math/rand` is replaced with `crypto/rand` and `encoding/base64`. Both are standard library packages.

4. **Performance impact**: `crypto/rand` is slower than `math/rand` because it calls the OS kernel, but this overhead is negligible for a one-time session ID generation at login time.

5. **Token length changes**: The original token was a 10-digit decimal number (up to 999,999,999). The fixed token is 24 characters (base64-encoded 16 bytes, 128 bits of entropy). This is longer but still reasonable for a session cookie.
