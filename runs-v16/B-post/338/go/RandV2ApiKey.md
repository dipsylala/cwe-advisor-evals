## Verdict

CWE-338 confirmed. The code uses `rand.IntN()` from `math/rand/v2` to generate API key material, which is cryptographically weak and predictable. API keys are security-sensitive long-lived credentials that require cryptographic randomness.

## Source

**File**: `evals/cases/338/go/RandV2ApiKey/RandV2ApiKey.go`, lines 24–25

**Data flow**: `rand.IntN(len(keyAlphabet))` produces a weak pseudo-random index, used to select bytes into the `key` array. The resulting 32-byte value is stored as a long-lived API key in the `apiKeys` map and returned to the caller in the HTTP response.

**Sink**: The `math/rand/v2.Intn()` call at line 24. Although `math/rand/v2` auto-seeds from OS randomness in Go 1.20+, the package's own documentation warns that its outputs "might be easily predictable regardless of how it's seeded" — enough observed output allows an attacker to reconstruct the generator's internal state and predict future API keys.

## Fix

Replace the weak PRNG loop with `crypto/rand.Reader`:

```go
package evalcases

import (
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"net/http"
)

const keyAlphabet = "abcdefghijklmnopqrstuvwxyz0123456789"

var apiKeys = map[string]string{}

// IssueAPIKey mints a long-lived API key for the named account.
func IssueAPIKey(w http.ResponseWriter, r *http.Request) {
	account := r.FormValue("account")
	if account == "" {
		http.Error(w, "account required", http.StatusBadRequest)
		return
	}

	key := make([]byte, 32)
	_, err := rand.Read(key)
	if err != nil {
		http.Error(w, "key generation failed", http.StatusInternalServerError)
		return
	}

	keyHex := hex.EncodeToString(key)
	apiKeys[keyHex] = account
	fmt.Fprint(w, keyHex)
}
```

**Changes**:
1. Replace the import `"math/rand/v2"` with `"crypto/rand"` and add `"encoding/hex"`
2. Remove the loop that indexes into `keyAlphabet` using `rand.IntN()`
3. Use `crypto/rand.Read()` to fill the 32-byte buffer directly with cryptographically secure random bytes
4. Encode the bytes as hex (ASCII-safe representation) for transport in HTTP
5. Add error handling for the `Read()` call; return HTTP 500 if randomness fails (OS-level randomness exhaustion is a critical condition)

This approach sizes the key in bytes (32 bytes = 256 bits) and uses the OS-backed cryptographic source. The hex encoding makes the key both transport-safe and reduces the byte-to-character bias that would occur if indexing into an alphabet by modulo.

## Explanation

`math/rand/v2.Intn()` is a fast, deterministic pseudo-random algorithm unsuitable for cryptographic use. Even with automatic OS seeding, the internal state can be reconstructed from observed output, allowing an attacker to predict subsequent API keys. Since API keys are long-lived credentials that grant account access, this is a direct authentication bypass.

The fix replaces the weak PRNG with `crypto/rand.Reader`, which draws from the OS's cryptographic source (`getrandom(2)` on Linux, `ProcessPrng` on Windows) and requires no seeding. Filling a 32-byte buffer directly, then encoding to hex, provides:
- **Cryptographic strength**: OS-backed entropy that cannot be predicted from observed values
- **Transport safety**: Hex encoding produces printable ASCII that survives HTTP headers and JSON
- **Proper sizing**: 32 bytes (256 bits) is appropriate for a long-lived session or API key token
- **Error handling**: If `crypto/rand.Read()` fails, the request fails rather than falling back to a weak value

## Behaviour changes

- **Return value**: The API key format changes from direct alphabet indexing to hex-encoded 32 random bytes. Callers receive a longer, fixed-format string (64 hex characters for 32 bytes).
- **Error path**: The function now returns HTTP 500 if `crypto/rand.Read()` fails. Under normal operation, OS randomness is reliable; this error indicates a system-level failure (e.g., entropy exhaustion) that should not be masked.
- **No backwards compatibility**: Existing API keys generated by the old code are not affected, but new keys follow the new format.
