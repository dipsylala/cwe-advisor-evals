## Verdict

**Confirmed CSRF vulnerability.** The GET `/account/delete` route performs account deletion without CSRF token validation. While the application correctly implements `doubleCsrfProtection` for POST, PUT, and DELETE methods, CSRF middleware does not validate GET requests. A malicious link or image tag embedded on an external site can trigger account deletion for any logged-in user.

## Source

**File:** accountRoutes.js, line 53  
**Route:** `app.get('/account/delete', requireSession, deleteAccountHandler)`  
**Sink:** `deleteAccountHandler` function (line 25-28) executes account deletion via `accounts.delete(req.session.userId)`  
**Vulnerability type:** State-changing operation (GET) lacking CSRF token validation

The route is documented in the code as a "convenience link for the 'delete my account' confirmation email button" (lines 47-51), meaning it exists so links can trigger the action. However, it bypasses the `doubleCsrfProtection` middleware entirely because middleware runs only on non-safe (POST/PUT/DELETE) methods.

## Fix

Extract `generateCsrfToken` from the `doubleCsrf` initialization and add two changes:

1. **Update the doubleCsrf destructuring** to include `generateCsrfToken`:
```javascript
const { doubleCsrfProtection, generateCsrfToken } = doubleCsrf({
  getSecret: () => process.env.CSRF_SECRET,
  getSessionIdentifier: (req) => req.session.id,
  cookieName: 'x-csrf-token',
  cookieOptions: { sameSite: 'lax', secure: true },
});
```

2. **Replace the GET route and add a protected POST route:**

Replace line 53:
```javascript
app.get('/account/delete', requireSession, deleteAccountHandler);
```

With:
```javascript
app.get('/account/delete', requireSession, (req, res) => {
  const token = generateCsrfToken(req, res);
  const html = `
    <html>
      <head><title>Confirm Account Deletion</title></head>
      <body>
        <h1>Confirm Account Deletion</h1>
        <form method="POST" action="/account/delete">
          <input type="hidden" name="_csrf" value="${token}">
          <p>Are you sure you want to delete your account? This action cannot be undone.</p>
          <button type="submit">Delete My Account</button>
          <a href="/">Cancel</a>
        </form>
      </body>
    </html>
  `;
  res.send(html);
});

app.post('/account/delete', requireSession, doubleCsrfProtection, deleteAccountHandler);
```

## Explanation

The fix addresses the CSRF gap by keeping the GET route for email links while enforcing CSRF token validation on the actual state-changing operation. The GET `/account/delete` now returns a confirmation page with an embedded CSRF token generated by `generateCsrfToken()` and rendered into a hidden form field. When the user submits the confirmation form, the POST `/account/delete` route validates the token via `doubleCsrfProtection` middleware before executing `deleteAccountHandler`.

This preserves backward compatibility with existing email confirmation links (which still land on `/account/delete` via GET) while closing the CSRF vector. The token is scoped to the user's session via the `getSessionIdentifier` function, ensuring a token minted for one user cannot validate for another.

The `_csrf` field name matches the expected form field for the `csrf-csrf` middleware when tokens travel in the request body.

## Behaviour changes

- **GET `/account/delete`:** Previously triggered immediate account deletion; now returns an HTML confirmation page with a form that must be submitted to proceed (both existing links and direct requests now show the confirmation page instead).
- **POST `/account/delete`:** New endpoint that performs the deletion and requires a valid CSRF token. Requests without a valid token receive a 403 response from `doubleCsrfProtection`.
- **Client impact:** Existing email confirmation links now render a confirmation form instead of deleting immediately, requiring user interaction (form submission). This is a necessary behaviour change to close the CSRF vector; automated email clients cannot trigger deletion without user action in the browser.
