## Verdict

CONFIRMED - Path Traversal via `Path.Combine()` with rooted user input.

## Source

The vulnerability originates at line 15 where the `file` parameter is received from an untrusted HTTP query string via ASP.NET's `[FromQuery]` attribute. The model binding framework decodes the query parameter, and this decoded value is passed directly into the path construction logic without validation.

## Fix

Apply canonicalization and containment validation using `Path.GetFullPath()` and `Path.GetRelativePath()` before accessing the file. The fix validates that the resolved path remains within the intended base directory.

### File: PathCombineAbsoluteOverride.cs

```csharp
using Microsoft.AspNetCore.Mvc;

namespace EvalCases.Controllers;

[ApiController]
[Route("api/[controller]")]
public class ReportsController : ControllerBase
{
    // Reports generated by the application are normally written here and
    // nowhere else; the intent is that this endpoint can only ever serve
    // files from this directory.
    private readonly string _reportsRoot = @"C:\App\Data\Reports";

    [HttpGet("export")]
    public IActionResult ExportReport([FromQuery] string file)
    {
        // Canonicalize and validate that 'file' is a relative path within the reports root
        var reportPath = Path.Combine(_reportsRoot, file);
        var fullPath = Path.GetFullPath(reportPath);
        var relativePath = Path.GetRelativePath(_reportsRoot, fullPath);

        // Reject if the path is outside the base directory
        if (relativePath.StartsWith("..") || Path.IsPathRooted(relativePath))
        {
            return BadRequest();
        }

        var reportText = System.IO.File.ReadAllText(fullPath);

        return Content(reportText, "text/plain");
    }
}
```

## Explanation

The vulnerability exists because `Path.Combine()` has a documented behavior: when any argument after the first is rooted (absolute), it discards all earlier components and returns the later path unchanged. This means an attacker providing an absolute path like `C:\Windows\System32\file.txt` or `/etc/passwd` will cause `Path.Combine(_reportsRoot, file)` to return the attacker-supplied absolute path, completely bypassing the intended directory restriction.

The fix:
1. **Canonicalizes** the combined path using `Path.GetFullPath()`, which resolves relative path components like `..` to their absolute form
2. **Validates containment** by computing the relative path from the base directory using `Path.GetRelativePath()` 
3. **Rejects** any path that escapes the base directory (indicated by a relative path starting with `..`) or any path that is rooted (absolute)
4. **Uses only the validated path** (`fullPath`) for the actual file operation, ensuring the checked value is the one accessed

This approach handles multiple attack vectors:
- Absolute paths (e.g., `C:\Windows\System32\cmd.exe`)
- Relative traversal sequences (e.g., `../../sensitive/file.txt`)
- Encoded sequences decoded by the framework (already decoded by ASP.NET model binding, so no double-decode issue)

## Behaviour changes

**Legitimate usage**: Normal relative file names like `"report.txt"` or `"archive\report.txt"` are accepted and read from the reports directory as intended. The relative path computation returns the filename itself, which does not start with `..` and is not rooted, so the containment check passes.

**Attack attempts**: Requests with traversal payloads or absolute paths now return HTTP 400 (Bad Request) instead of exposing files outside the intended directory. Examples of rejected paths:
- `../../../etc/passwd` → rejected (relative path starts with `..`)
- `C:\Windows\System32\drivers\etc\hosts` → rejected (rooted path, discarded by `Path.Combine` but caught by `Path.IsPathRooted()` check)
- `..\..\..\sensitive.txt` → rejected (relative path starts with `..`)

**Error handling**: Legitimate requests for non-existent files within the allowed directory still result in an exception from `File.ReadAllText()`, which the application can handle or allow to propagate as a 500 error.
