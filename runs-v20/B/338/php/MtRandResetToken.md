## Verdict

Confirmed. CWE-338 (Use of a Cryptographically Weak PRNG) is real and exploitable at `MtRandResetToken.php:18`.

## Source

The security-relevant value is the password-reset token generated for a user who successfully looked up an account by email (`$userId` resolved at line 10-14). `mt_rand()` at line 18 is the source of that token's randomness; it is a Mersenne Twister non-cryptographic generator whose output is predictable/reproducible and not fit for a security token. The call also mixes in a client-controlled lower/upper bound (`$seed = $request['client_seed'] ?? 0`, line 16), so the range itself is attacker-influenced in addition to the generator being weak - compounding the weakness rather than mitigating it.

## Fix

### File: MtRandResetToken.php

```php
<?php

// Handles a "forgot password" request and emails the user a reset link.
function handlePasswordResetRequest(PDO $db, array $request): void
{
    $email = $request['email'] ?? '';

    $stmt = $db->prepare('SELECT id FROM users WHERE email = ?');
    $stmt->execute([$email]);
    $userId = $stmt->fetchColumn();

    if ($userId === false) {
        return;
    }

    $token = random_int(0, 999999);

    $update = $db->prepare('UPDATE users SET reset_token = ?, reset_expires = ? WHERE id = ?');
    $update->execute([$token, time() + 3600, $userId]);

    mail($email, 'Password Reset', 'Use this code to reset your password: ' . $token);
}
```

## Explanation

The fix replaces `mt_rand($seed, $seed + 999999)` with `random_int(0, 999999)`, PHP's cryptographically secure integer generator (per the knowledge base's PHP CWE-338 guidance: "Replace `rand()`/`mt_rand()` with `random_int()` for integer values"). `random_int()` is backed by the OS CSPRNG and does not accept or need an application-supplied seed, so the fix also removes the `$seed = $request['client_seed'] ?? 0` assignment entirely rather than feeding client input into the bound - per the same guidance ("Never seed or predict CSPRNG output", "Remove any custom seeding logic for PRNGs"). Letting a caller pick the base of the reset-code range let an attacker fix the low end of the search space themselves, on top of the generator already being predictable; dropping that input closes both problems at once. The output range (0-999999) is preserved unchanged from the original code's default behavior (`$seed` defaulted to `0`, giving `mt_rand(0, 999999)`), so the value's type, digit-count contract with the "code" wording in the email, and the DB column it is written to are all unaffected - only the generation mechanism and the removal of attacker influence over the range change.

## Behaviour changes

- The reset code's value space is unchanged (still an integer drawn from 0 to 999999 inclusive) but is now generated by a CSPRNG instead of Mersenne Twister, so it is no longer predictable or reproducible by an attacker who observes other outputs or knows the process state.
- The `client_seed` request field is no longer read or honored. Any caller previously relying on it to influence the reset-code range (there is no legitimate reason to - the guidance explicitly forbids seeding a secure generator) will see that input silently ignored; the code generated is drawn uniformly from 0-999999 regardless.
- Checked with `php -l` against the fixed file (copied to a scratch location, not the case fixture): "No syntax errors detected". `random_int()` is a PHP core function (bundled since PHP 7.0, well within the PHP 8.5 CLI used for the check) requiring no new import or dependency, so no library/version recommendation applies to this fix.
