## Verdict

exploitable

- cwe_id: CWE-79
- location: ConfirmationPageRenderer.php, line 11 (sink); tainted value originates in TicketController.php
- confidence: high

## Source

`$_POST['comment']` (and, via the same `$message` string, `$_POST['customer_name']`) read in `TicketController::handleSubmit()`. Neither value is validated or encoded. The call chain:

1. `TicketController::handleSubmit()` reads `$_POST['comment']` (and `$_POST['customer_name']`) and passes both, unmodified, to `TicketService::createTicket()`.
2. `TicketService::createTicket()` generates a server-side `$ticketId` via `uniqid('tkt_', true)` (not attacker-controlled) and forwards `$customerName` and `$comment` unchanged to `NotificationDispatcher::sendConfirmation()`.
3. `NotificationDispatcher::sendConfirmation()` builds `$message` by string-interpolating `$customerName` and concatenating `$comment` directly, with no encoding.
4. `ConfirmationPageRenderer::render()` echoes `$message` straight into the HTML body: `echo '<p>' . $message . '</p>';` (line 11). This is the sink - a browser rendering this response executes any markup/script contained in `$comment` or `$customer_name`.

`$ticketId` is also interpolated into the `data-ticket-id` attribute on the preceding line, but it is server-generated by `uniqid()`, never attacker-influenced, so it carries no exploitable taint and is not part of this finding.

## Fix

### File: ConfirmationPageRenderer.php
```php
<?php

// Renders the HTML confirmation page shown after a ticket is filed.
class ConfirmationPageRenderer
{
    public function render(string $ticketId, string $message): void
    {
        echo '<!DOCTYPE html><html><head><title>Ticket Submitted</title></head><body>';
        echo '<div class="confirmation" data-ticket-id="' . $ticketId . '">';
        echo '<p>' . htmlspecialchars($message, ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML5, 'UTF-8') . '</p>';
        echo '</div></body></html>';
    }
}
```

## Explanation

The weakness is missing output encoding at the point where untrusted data is written into the HTML response, not the construction of `$message` upstream - per the CWE-79 guidance, encoding belongs at each output sink. `ConfirmationPageRenderer::render()` is that sink: it is the only place that writes `$message` to the HTTP response, so encoding there closes the path regardless of how many upstream layers touch the string, and matches the PHP-specific guidance's canonical pattern (`htmlspecialchars()` with `ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML5` and explicit `'UTF-8'`). `ENT_QUOTES` neutralizes both `"` and `'` so an attacker-supplied value cannot break out of a surrounding attribute if the template around it changes later; `ENT_SUBSTITUTE` replaces invalid UTF-8 with a placeholder instead of silently emptying the whole string; `ENT_HTML5` selects the correct entity table for an HTML5 document. `$ticketId` was left unescaped because it is generated server-side by `uniqid()` and never derived from request input, so it is not part of the weakness being fixed.

## Behaviour changes

- Legitimate customer-supplied text containing `<`, `>`, `&`, `"`, or `'` (e.g. "Ticket <#5> & note's fine") is now rendered as literal text via HTML entities instead of being interpreted as markup. This is the intended effect of the fix, not a regression: it was previously executed/rendered as HTML, which is the vulnerability. Verified with a payload of `<script>alert(1)</script>` embedded in a comment containing an apostrophe: output shows `&lt;script&gt;alert(1)&lt;/script&gt;` and `&apos;`, both of which render identically to the original characters in a browser.
- No other output, argument, return value, or control flow changed. `$ticketId`'s attribute rendering is untouched.
- verification: `php -l` on the fixed file reported no syntax errors. Additionally ran the fixed `render()` against a live PHP 8.5.8 CLI with a malicious `$message` (`<script>` payload plus an apostrophe) via a standalone harness outside the case directory; output confirmed the script payload is neutralized to text and the apostrophe still displays correctly to a user.
- assumptions: none - the sink and its context were unambiguous from the provided call chain.
