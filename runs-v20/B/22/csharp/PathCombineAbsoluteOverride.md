## Verdict

exploitable

- cwe_id: CWE-22 (Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal'))
- location: `PathCombineAbsoluteOverride.cs`, line 23 (sink), constructed at line 20
- confidence: high

## Source

`ExportReport(string file)` binds the `file` query-string parameter (`[FromQuery] string file`) directly from the HTTP request with no validation. This value is attacker-controlled.

Data flow: `file` (query param, untrusted) -> `Path.Combine(_reportsRoot, file)` (line 20) -> `reportPath` -> `System.IO.File.ReadAllText(reportPath)` (line 23, sink).

`Path.Combine` is documented by Microsoft to discard every earlier argument outright when a later argument is itself a rooted path. Because `file` is untrusted and unchecked, a request such as `?file=C:\Windows\win32.ini` (or a UNC path) makes `Path.Combine` drop `_reportsRoot` entirely, and `File.ReadAllText` reads whatever absolute path the attacker supplied - a full path-traversal / arbitrary file read, not merely an escape via `../`. A relative-traversal payload such as `..\..\..\Windows\win32.ini` is also not blocked, since there is no canonicalization or containment check at all.

## Fix

### File: PathCombineAbsoluteOverride.cs

```csharp
using Microsoft.AspNetCore.Mvc;

namespace EvalCases.Controllers;

[ApiController]
[Route("api/[controller]")]
public class ReportsController : ControllerBase
{
    // Reports generated by the application are normally written here and
    // nowhere else; the intent is that this endpoint can only ever serve
    // files from this directory.
    private readonly string _reportsRoot = @"C:\App\Data\Reports";

    [HttpGet("export")]
    public IActionResult ExportReport([FromQuery] string file)
    {
        // Path.Combine discards the base directory outright when 'file' is
        // itself rooted (Microsoft docs: a later rooted argument makes every
        // earlier component vanish from the result), so the containment
        // check below has to run against the canonicalized, combined path -
        // not the raw 'file' value.
        var combinedPath = Path.Combine(_reportsRoot, file);
        var fullPath = Path.GetFullPath(combinedPath);

        // Component-aware containment check: compare with GetRelativePath
        // rather than a raw string prefix, so a sibling directory such as
        // C:\App\Data\Reports-secret cannot pass. Reject outright rather
        // than stripping the traversal sequence.
        var relativePath = Path.GetRelativePath(_reportsRoot, fullPath);
        var isOutsideRoot =
            relativePath == ".." ||
            relativePath.StartsWith(".." + Path.DirectorySeparatorChar) ||
            relativePath.StartsWith(".." + Path.AltDirectorySeparatorChar) ||
            Path.IsPathRooted(relativePath);

        if (isOutsideRoot)
        {
            return BadRequest("Invalid file path.");
        }

        var reportText = System.IO.File.ReadAllText(fullPath);

        return Content(reportText, "text/plain");
    }
}
```

## Explanation

The vulnerability was that `Path.Combine` never validates its inputs: per Microsoft's own documentation, if `file` is a rooted path (an absolute Windows path, a drive-qualified path, or a UNC path), `Path.Combine` discards `_reportsRoot` and returns `file` unchanged, so the "restricted directory" was never actually enforced. The fix keeps the same `Path.Combine` call (so relative filenames behave exactly as before) but immediately canonicalizes the result with `Path.GetFullPath()`, then checks containment with `Path.GetRelativePath(_reportsRoot, fullPath)` rather than a raw string prefix - this is component-aware, so a sibling directory that merely starts with the same characters (e.g. `C:\App\Data\Reports-Legacy`) cannot pass. If the relative result is `..`, starts with `..` plus either directory-separator form, or is itself rooted (which `GetRelativePath` returns when the two paths are on different drives), the request is rejected before the file system is touched. The same canonicalized `fullPath` variable is what gets passed to `File.ReadAllText`, so there is no re-derivation gap between the check and the sink.

## Behaviour changes

- Requests where `file` resolves outside `_reportsRoot` (absolute paths, UNC paths, `..` traversal, or a different drive) now return `400 Bad Request` instead of either succeeding (the vulnerable case) or throwing an unhandled `IOException`/`UnauthorizedAccessException` for a `..`-relative path that happened to still resolve outside the root. This is the intended effect of the fix, not a side effect - it converts an information-disclosure success or an unhandled exception into an explicit, safe rejection.
- For any `file` value that resolves inside `_reportsRoot` (the legitimate, in-scope case), behavior is unchanged: `File.ReadAllText` is called with the same resolved absolute path `Path.Combine` + `Path.GetFullPath` would have produced, and the response is identical (`Content(reportText, "text/plain")`).
- No change to the success return type, the failure behavior for a missing-but-in-scope file (still an unhandled `FileNotFoundException` surfacing as a 500, matching the original contract), or any other endpoint.
