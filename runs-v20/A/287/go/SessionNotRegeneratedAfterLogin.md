## Verdict

Confirmed. `LoginHandler` promotes whatever session cookie arrived on the request to an
authenticated one instead of issuing a fresh session on login. A pre-existing cookie -
including one an attacker planted on the victim's browser before the victim authenticated
(classic session fixation) - is decoded into `session.Values` and then merely has `userID`
and `username` added to it, so any state that decoded cookie already carried survives into
the authenticated session unchanged.

## Source

The tainted input is the inbound `Cookie: session-name=...` header on the request handled by
`LoginHandler` (`r` in `store.Get(r, "session-name")`, line 48). This cookie is not guaranteed
to have been issued to the current user in the current login flow - it can be a cookie an
attacker obtained from the server beforehand (e.g. an anonymous/pre-auth session) and fixed
onto the victim's browser. `store.Get` decodes it into `session.Values`, and that decoded map
is the value that flows, unmodified except for two added keys, into the authenticated session
written out by `session.Save` at line 54.

## Fix

### File: login_handler.go
```go
// Package auth implements the login endpoint for the accounts service.
//
// Session store: gorilla/sessions v1.4.0 (the latest release as of this
// writing; the project has no built-in session identifier rotation - see
// upstream issue #235, which remains open).
package auth

import (
	"log"
	"net/http"

	"github.com/gorilla/sessions"
)

// store is the process-wide gorilla/sessions cookie store, configured at
// startup with a secret loaded from the environment.
var store = sessions.NewCookieStore([]byte(sessionSecret()))

// User represents an authenticated account record loaded from the database.
type User struct {
	ID       int64
	Username string
	// PasswordHash is omitted from this sample; credential verification
	// happens in verifyCredentials before LoginHandler is reached.
}

// LoginHandler authenticates a submitted username/password pair and starts
// an authenticated session for the caller.
func LoginHandler(w http.ResponseWriter, r *http.Request) {
	if err := r.ParseForm(); err != nil {
		http.Error(w, "bad request", http.StatusBadRequest)
		return
	}

	username := r.FormValue("username")
	password := r.FormValue("password")

	user, err := verifyCredentials(username, password)
	if err != nil {
		http.Error(w, "invalid username or password", http.StatusUnauthorized)
		return
	}

	// Password check succeeded above. store.Get (and store.New - it runs the
	// identical decode) both populate session.Values from whatever cookie
	// the request carried, including one an attacker may have set on the
	// victim's browser before they logged in. gorilla/sessions' CookieStore
	// has no separate server-side session identifier to rotate (Session.ID
	// is documented as unused by CookieStore, and CookieStore.Save encodes
	// only Values into the cookie) - the cookie's content is the entire
	// session state. So the fixation-safe equivalent of "issue a new
	// identifier" here is to discard whatever was decoded and build the
	// authenticated session from a clean map, so nothing from a
	// pre-authentication cookie carries forward into it.
	session, _ := store.Get(r, "session-name")
	session.Values = make(map[interface{}]interface{})
	session.Values["userID"] = user.ID
	session.Values["username"] = user.Username

	if err := session.Save(r, w); err != nil {
		log.Printf("failed to save session: %v", err)
		http.Error(w, "internal server error", http.StatusInternalServerError)
		return
	}

	w.WriteHeader(http.StatusOK)
	w.Write([]byte("logged in"))
}

// verifyCredentials looks up the account by username and checks the
// submitted password against the stored hash. Implementation omitted -
// this sample is scoped to the session-handling gap in LoginHandler.
func verifyCredentials(username, password string) (*User, error) {
	panic("not implemented in this sample")
}

// sessionSecret loads the cookie-store signing key from the environment.
// Implementation omitted - not relevant to this sample.
func sessionSecret() string {
	panic("not implemented in this sample")
}
```

## Explanation

Checked against the actual `gorilla/sessions` v1.4.0 source: `CookieStore.Get` and
`CookieStore.New` both call the identical decode - if a `session-name` cookie is present on
the request, its bytes are unmarshalled straight into `session.Values`, and this happens
regardless of which of the two methods is called. So swapping `store.Get` for `store.New`
changes nothing about whether a planted cookie's content is honored; it decodes it exactly
the same way. `Session.ID` is documented as "generated by stores... should not be used for
user data" and, for `CookieStore` specifically, is never even written into the cookie -
`CookieStore.Save` encodes only `session.Values`. There is no separate opaque identifier for
a `CookieStore`-backed session to regenerate the way a database- or filesystem-backed store's
ID could be; the cookie's signed content is the entirety of the session.

The fix therefore targets what the store actually persists: immediately after obtaining the
session, `session.Values` is replaced with a fresh, empty map before any authenticated data is
written into it. This guarantees that whatever was decoded from the incoming request's
cookie - attacker-fixed or otherwise - is discarded rather than carried forward, and the
cookie `session.Save` emits is built solely from data set after successful credential
verification. Because `CookieStore.Save` issues a `Set-Cookie` for the same name, this
response also fully supersedes whatever cookie value the browser held before, so the client
ends the request holding only the newly-issued, values-reset session; no separate
invalidation step is required for a pure cookie store. A test for this fix should authenticate
with a pre-set `session-name` cookie carrying an arbitrary decodable key (signed with the same
store secret) and assert that key is absent from the post-login session, while `userID` and
`username` are present and correct - asserting only that login succeeds would not catch the
regression, since the vulnerable version also returns 200.
