# PathCombineAbsoluteOverride - CWE-22 Remediation

## Verdict

**Exploitable** - High confidence. The vulnerability is confirmed and present in the original code. An attacker can supply an absolute path as the `file` query parameter, which `Path.Combine()` will substitute directly in place of the intended root directory, bypassing the containment restriction.

## Source

The attack surface is the `[FromQuery] string file` parameter in the `ExportReport` action method (line 15). User input flows directly into `Path.Combine(_reportsRoot, file)` at line 20 without validation. `Path.Combine()` has documented behavior: when any argument after the first is rooted (begins with a drive letter or `\` on Windows), all earlier arguments are discarded, and the result is that rooted path. An attacker passing `file="C:\Windows\System32\config\SAM"` causes `Path.Combine()` to return the attacker's path unchanged, redirecting the read to an unauthorized location.

The sink is `System.IO.File.ReadAllText(reportPath)` at line 23, which executes the traversal and reads the arbitrary file.

## Fix

### File: PathCombineAbsoluteOverride.cs

```csharp
using Microsoft.AspNetCore.Mvc;

namespace EvalCases.Controllers;

[ApiController]
[Route("api/[controller]")]
public class ReportsController : ControllerBase
{
    // Reports generated by the application are normally written here and
    // nowhere else; the intent is that this endpoint can only ever serve
    // files from this directory.
    private readonly string _reportsRoot = @"C:\App\Data\Reports";

    [HttpGet("export")]
    public IActionResult ExportReport([FromQuery] string file)
    {
        // Validate that file is not null or empty
        if (string.IsNullOrEmpty(file))
        {
            return BadRequest("File parameter is required");
        }

        // Combine paths and canonicalize
        var reportPath = Path.Combine(_reportsRoot, file);
        var fullPath = Path.GetFullPath(reportPath);
        var canonicalRoot = Path.GetFullPath(_reportsRoot);

        // Validate containment using GetRelativePath
        var relativePath = Path.GetRelativePath(canonicalRoot, fullPath);

        // Reject if path escapes the root directory
        if (relativePath == ".." ||
            relativePath.StartsWith(".." + Path.DirectorySeparatorChar) ||
            relativePath.StartsWith(".." + Path.AltDirectorySeparatorChar) ||
            Path.IsPathRooted(relativePath))
        {
            return BadRequest("Access denied: path traversal detected");
        }

        var reportText = System.IO.File.ReadAllText(fullPath);

        return Content(reportText, "text/plain");
    }
}
```

## Explanation

The fix applies three layers of defense following CWE-22 remediation guidance for C#:

1. **Canonicalization**: `Path.GetFullPath()` normalizes both the combined path and the root directory, resolving all `..` components and relative references to absolute form. This ensures consistent comparison.

2. **Containment validation**: `Path.GetRelativePath(canonicalRoot, fullPath)` computes the relative path from the approved root to the resolved file path. If this relative path attempts to escape (starts with `..`, contains `..` as a path component, or is itself rooted), the access is rejected. This method is component-aware and avoids the string-prefix pitfall where `startsWith("/app/uploads")` incorrectly passes `/app/uploads-secret`.

3. **Rejection over stripping**: Invalid paths trigger a 400 BadRequest response rather than attempting to "repair" or filter the input, which would hide the attack attempt from logs and allow sophisticated payloads like `....//` (which becomes `../` after non-recursive removal) to succeed.

The fix uses `Path.DirectorySeparatorChar` and `Path.AltDirectorySeparatorChar` to handle both forward and backward slashes correctly on Windows, where `GetRelativePath()` may return either form.

## Behaviour changes

1. **Added null/empty validation** for the `file` parameter (lines 20-23). Reason: Defensive programming to reject invalid input early, preventing exceptions and clarifying the error response to the client.

2. **Added intermediate variables** `reportPath`, `fullPath`, and `canonicalRoot` (lines 26-28). Reason: These hold the canonicalized paths used in both the containment check and the file read, ensuring we validate the exact value we use and avoiding re-derivation of the path, which could lead to TOCTTOU or inconsistency bugs.

3. **Changed the sink argument** from `reportPath` to `fullPath` (line 38). Reason: `reportPath` may still contain relative components or be non-canonical; `fullPath` is the verified, canonicalized absolute path that we confirmed stays within the root.

4. **Added access denial response** (lines 31-36). Reason: The original code made no check, so it always proceeded to the file read. The fixed code now rejects traversal attempts with an explicit 400 BadRequest and a reason message, making the vulnerability unexploitable.

5. **No behavior change to legitimate requests**: When `file` is a relative path like `"report.txt"` or a subdirectory like `"monthly\january.txt"`, the canonicalization and containment check pass, and the file is read as before. The response code, content, and return type remain identical for valid inputs.
