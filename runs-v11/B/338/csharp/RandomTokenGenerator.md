## Verdict
CONFIRMED — CWE-338 finding is valid and exploitable.

## Source
HTTP query parameter `seed` (line 10: `[FromQuery] int seed`).

## Fix

**Vulnerable code (line 13):**
```csharp
var rng = new Random(seed);
```

**Fixed code:**
```csharp
var tokenBytes = new byte[16];
RandomNumberGenerator.GetBytes(tokenBytes);
```

Replace the entire block:
```csharp
var rng = new Random(seed);
var tokenBytes = new byte[16];
rng.NextBytes(tokenBytes);
```

With:
```csharp
var tokenBytes = new byte[16];
RandomNumberGenerator.GetBytes(tokenBytes);
```

Add the `using System.Security.Cryptography;` directive at the top of the file if not already present.

## Explanation

The vulnerability arises from two compounding weaknesses:

1. **Weak PRNG**: `System.Random` is a general-purpose, seeded PRNG not designed for cryptographic use. Given a seed, its entire output sequence is deterministic and predictable.

2. **Attacker-controlled seed**: The `seed` parameter comes directly from an HTTP query parameter. An attacker can supply any seed value, fully determining the "random" token that will be generated.

A password reset token is a critical security context: an attacker who predicts the token can gain unauthorized account access. The fix replaces `System.Random` with `RandomNumberGenerator.GetBytes()`, which draws from the OS cryptographic entropy source and is not seeded with user input. The generated bytes are then Base64-encoded for transport in the response, preserving the original intended behavior while eliminating predictability.

The `seed` parameter itself is now unused; removing it from the method signature is recommended in a follow-up fix, as it has no security purpose.

## Behaviour changes

- **Random token generation**: Tokens are now cryptographically unpredictable instead of deterministic from the seed parameter.
- **No replay risk**: Each call generates a fresh token independent of any prior calls, eliminating the risk of duplicate tokens.
- **Performance**: Minimal—`RandomNumberGenerator.GetBytes()` uses the same OS cryptographic API and will not meaningfully impact request latency.
- **Compatibility**: Requires .NET 6 or later. For .NET 5 or Framework, use `RandomNumberGenerator.Create()` with `GetBytes(byte[])` as a fallback.
