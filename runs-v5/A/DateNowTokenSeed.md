## Verdict

Confirmed. The password reset token is generated with `Math.random()`, a non-cryptographic PRNG. Its output is not suitable for security tokens: it is not designed to be unpredictable, and depending on the JS engine its internal state can be inferred from a handful of observed outputs, letting an attacker predict or brute-force future/past tokens and hijack another user's password reset flow.

## Source

`e:/Github/cwe-advisor/evals/cases/330/javascript/DateNowTokenSeed/DateNowTokenSeed.js`, line 15:

```js
const token = Math.random().toString(36).substring(2);
```

This value is used directly as the reset token, stored as the key in `resetTokens` and emailed to the user as the `token` query parameter (lines 17-19).

## Fix

```js
const crypto = require('crypto');
...
const token = crypto.randomBytes(32).toString('hex');
```

Replace the `Math.random().toString(36).substring(2)` call with a value generated by Node's `crypto` module, which is backed by the OS CSPRNG:

```js
const express = require('express');
const crypto = require('crypto');
const router = express.Router();

const resetTokens = new Map();

router.post('/forgot-password', (req, res) => {
  const email = req.body.email;

  if (!email || typeof email !== 'string') {
    return res.status(400).json({ error: 'email is required' });
  }

  const token = crypto.randomBytes(32).toString('hex');

  resetTokens.set(token, { email, expires: Date.now() + 3600000 });

  sendResetEmail(email, token);

  res.json({ message: 'If that email exists, a reset link was sent.' });
});
```

`crypto.randomBytes(32)` yields 256 bits of entropy, hex-encoded to a 64-character token, which is both unpredictable and comfortably resistant to brute-force guessing within the token's one-hour lifetime.

## Explanation

`Math.random()` is specified only for statistical randomness (e.g. simulations, non-security sampling), not cryptographic unpredictability. V8 and other engines use fast, non-cryptographic PRNGs (e.g. xorshift128+) whose internal state is small and, in published research, recoverable from a modest number of observed outputs - after which every past and future value the generator produces can be predicted. For a password reset token, that means an attacker who can observe or influence a few generated tokens (or who simply brute-forces the comparatively small output space of `toString(36)` on a 0-1 float) can guess a valid token for another account and take over the reset flow.

`crypto.randomBytes()` draws from the platform's cryptographically secure random source (`/dev/urandom` on Linux, `CryptGenRandom`/`BCryptGenRandom` on Windows) and gives no practical way to predict past or future output from observed values. Using it for the token, combined with the existing time-limited, single-use storage in `resetTokens`, keeps the reset mechanism resistant to guessing attacks. No other part of the flow needs to change: the token is still used as a Map key and appended to the reset URL the same way, so callers of `sendResetEmail` and the `resetTokens` map are unaffected by the swap.
