## Verdict

CWE-79 (Cross-Site Scripting), exploitable. `ConfirmationPageRenderer.php` line 11 echoes a string built from two unescaped POST fields directly into the HTML response body. Confidence: high.

## Source

- `TicketController::handleSubmit()` (`TicketController.php:11-12`) reads `$_POST['customer_name']` (trimmed only, not encoded) and `$_POST['comment']` (used as-is) - both fully attacker-controlled.
- These are passed unchanged through `TicketService::createTicket()` (`TicketService.php:9-17`), which does not transform or encode either value before forwarding them.
- `NotificationDispatcher::sendConfirmation()` (`NotificationDispatcher.php:9-16`) concatenates both tainted values, without escaping, into a single string: `$message = $greeting . " We've logged ticket {$ticketId}. Your note: " . $comment;` where `$greeting` itself embeds `$customerName`.
- Sink: `ConfirmationPageRenderer::render()` (`ConfirmationPageRenderer.php:11`) - `echo '<p>' . $message . '</p>';` writes the tainted `$message` into the HTML document body with no output encoding.

Note: `$ticketId`, echoed at `ConfirmationPageRenderer.php:9` into a `data-ticket-id` attribute and interpolated into `$message`, is server-generated by `uniqid('tkt_', true)` in `TicketService.php:11` and is not attacker-controlled, so it is not part of this finding.

## Fix

Vulnerable code (`ConfirmationPageRenderer.php`):

```php
echo '<div class="confirmation" data-ticket-id="' . $ticketId . '">';
// SAST FINDING: CWE-79 reported here. Sink is the next statement.
echo '<p>' . $message . '</p>';
echo '</div></body></html>';
```

Fixed code:

```php
echo '<div class="confirmation" data-ticket-id="' . $ticketId . '">';
echo '<p>' . htmlspecialchars($message, ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML5, 'UTF-8') . '</p>';
echo '</div></body></html>';
```

No library recommendation is needed - `htmlspecialchars()` is a PHP core function.

## Explanation

`$message` mixes attacker-controlled `customer_name` and `comment` with static literal text, but the entire value renders into a single HTML context: text content inside a `<p>` element. Applying `htmlspecialchars()` with `ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML5` and explicit `'UTF-8'` at that sink converts `<`, `>`, `&`, `"`, and `'` in the composed string into their HTML entity equivalents, so any injected markup (e.g. `<script>`, an `onerror` attribute via `<img>`, or a quote-breakout attempt) is rendered as inert text rather than parsed as HTML. `ENT_QUOTES` covers both quote characters even though the immediate context is element body text, keeping the call safe if the same value is later reused inside an attribute. `ENT_SUBSTITUTE` ensures a malformed UTF-8 byte sequence becomes a replacement character instead of causing `htmlspecialchars()` to return an empty string and silently drop the whole message. Encoding is applied once, at the point of output, per the knowledge base's "encode at each sink" principle - the upstream layers (`TicketController`, `TicketService`, `NotificationDispatcher`) are left untouched since none of them render output themselves.

## Behaviour changes

- Any literal HTML metacharacters that legitimately appear in `customer_name` or `comment` (e.g. a name containing `&`, or a comment containing `<`) will now display as their literal characters in the rendered page (e.g. `&amp;`, `&lt;`) instead of being interpreted as markup - this is the intended effect of the fix, not a regression.
- The static apostrophe in "We've logged ticket..." is now HTML-entity-encoded (`&#039;`) as a side effect of encoding the whole composed string in one pass; it renders visually identical in the browser, so there is no user-visible change.
- No change to method signatures, return values, control flow, or error handling anywhere in the call chain. `ConfirmationPageRenderer::render()` still returns `void` and still echoes the same three-part page structure; only the second `echo` argument is now encoded.
