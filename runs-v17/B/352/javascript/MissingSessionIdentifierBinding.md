## Verdict

Exploitable. A CSRF token generated for one user's session can be reused in another user's session because the token validation is not bound to the session identifier.

## Source

The CSRF token is generated by `generateCsrfToken(req, res)` in the GET endpoint `/api/account/csrf-token` (accountRoutes.js:17), which calls the vulnerable `doubleCsrf()` configuration in csrfProtection.js that omits `getSessionIdentifier`.

## Fix

### File: csrfProtection.js

```javascript
'use strict';

const { doubleCsrf } = require('csrf-csrf');

// csrf-csrf v4+ requires getSessionIdentifier to bind each generated token to
// the session it was issued for. It must be provided to validate tokens against
// the correct session.
const {
  generateCsrfToken,
  doubleCsrfProtection
} = doubleCsrf({
  getSecret: () => process.env.CSRF_SECRET,
  getSessionIdentifier: (req) => req.sessionID,
  cookieName: 'x-csrf-token',
  cookieOptions: {
    sameSite: 'lax',
    secure: true,
    httpOnly: true
  }
});

module.exports = { generateCsrfToken, doubleCsrfProtection };
```

## Explanation

The vulnerability exists because the `doubleCsrf()` configuration was missing the `getSessionIdentifier` parameter. This parameter is required as of `csrf-csrf` v4 to bind each CSRF token to a specific session. Without it, the middleware validates tokens purely against the secret and cookie pair, allowing a token generated for one user to be replayed in another user's session. Adding `getSessionIdentifier: (req) => req.sessionID` extracts the session identifier from the request and binds each token to that session, ensuring that tokens cannot be reused across different sessions.

## Behaviour changes

None. The fix adds a required security binding without changing the API or return values. The `req.sessionID` property is provided by express-session middleware (already in use as evidenced by `req.session` checks in accountRoutes.js) and is guaranteed to be present for all authenticated requests reaching the CSRF endpoints.
