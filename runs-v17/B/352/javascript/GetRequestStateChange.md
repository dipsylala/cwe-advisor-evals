## Verdict

Confirmed. The GET route at line 53 performs a state-changing operation (account deletion) without CSRF protection. The `doubleCsrfProtection` middleware validates only POST, PUT, and DELETE requests—never GET—so this route bypasses the protection mechanism entirely even though the application's CSRF setup is otherwise correct.

## Source

The vulnerability is at line 53 in `accountRoutes.js`:

```javascript
app.get('/account/delete', requireSession, deleteAccountHandler);
```

The `deleteAccountHandler` function (lines 25–28) mutates server state by deleting the authenticated user's account:

```javascript
function deleteAccountHandler(req, res) {
  accounts.delete(req.session.userId);
  res.json({ status: 'deleted' });
}
```

**Data flow:** An attacker crafts a link (e.g., in an email or on a malicious website) pointing to `GET /account/delete`. When an authenticated victim clicks the link, the request carries the victim's active session cookie, satisfies the `requireSession` middleware, and invokes `deleteAccountHandler` without any CSRF token validation.

## Fix

### File: accountRoutes.js

```javascript
const express = require('express');
const cookieParser = require('cookie-parser');
const { doubleCsrf } = require('csrf-csrf');

const app = express();
app.use(express.json());
app.use(cookieParser());

const { doubleCsrfProtection, generateToken } = doubleCsrf({
  getSecret: () => process.env.CSRF_SECRET,
  getSessionIdentifier: (req) => req.session.id,
  cookieName: 'x-csrf-token',
  cookieOptions: { sameSite: 'lax', secure: true },
});

const accounts = new Map();

function requireSession(req, res, next) {
  if (!req.session || !req.session.userId) {
    return res.status(401).json({ error: 'authentication required' });
  }
  next();
}

function deleteAccountHandler(req, res) {
  accounts.delete(req.session.userId);
  res.json({ status: 'deleted' });
}

// Profile and email changes are correctly protected: doubleCsrfProtection
// validates the token on every one of these non-safe requests before the
// handler runs.
app.post('/account/profile', requireSession, doubleCsrfProtection, (req, res) => {
  const account = accounts.get(req.session.userId) || {};
  accounts.set(req.session.userId, { ...account, ...req.body });
  res.json({ status: 'updated' });
});

app.put('/account/email', requireSession, doubleCsrfProtection, (req, res) => {
  const account = accounts.get(req.session.userId) || {};
  accounts.set(req.session.userId, { ...account, email: req.body.email });
  res.json({ status: 'updated' });
});

app.delete('/account', requireSession, doubleCsrfProtection, deleteAccountHandler);

// Convenience link for the "delete my account" confirmation email button.
// GET route now renders a confirmation page with a CSRF-protected form instead of
// directly deleting the account. The doubleCsrfProtection middleware only validates
// POST/PUT/DELETE requests, never GET, so any state-changing operation on GET would
// bypass CSRF protection even though the app's middleware setup is correct.
// The fix: keep GET at this URL, have it render a confirmation form. The form POSTs
// to the CSRF-protected POST route below with the token included.
app.get('/account/delete', requireSession, (req, res) => {
  const csrfToken = generateToken(req, res);
  res.send(`
    <html>
      <body>
        <h1>Delete Account</h1>
        <p>Are you sure you want to delete your account? This cannot be undone.</p>
        <form method="POST" action="/account/delete">
          <input type="hidden" name="_csrf" value="${csrfToken}">
          <button type="submit">Delete My Account</button>
        </form>
      </body>
    </html>
  `);
});

// POST route handles the actual deletion with CSRF protection.
app.post('/account/delete', requireSession, doubleCsrfProtection, deleteAccountHandler);

module.exports = app;
```

## Explanation

The vulnerability arises because CSRF middleware in Express (and most frameworks) only validates non-safe HTTP methods (POST, PUT, DELETE, PATCH). The GET method is considered safe and never receives CSRF token validation, even when the route handler performs state changes.

The fix applies the **Synchronizer Token Pattern** at the correct HTTP verb:

1. **GET `/account/delete`** now serves a confirmation page with an embedded CSRF token generated by `generateToken(req, res)`. The token is bound to the user's session via the `getSessionIdentifier` callback.

2. **POST `/account/delete`** performs the actual deletion and is protected by the `doubleCsrfProtection` middleware. The middleware validates the `_csrf` token from the request body against the server's record before allowing the handler to run.

3. **Import addition:** `generateToken` is destructured from `doubleCsrf()` (already called at line 9) so the GET handler can mint a fresh token per request and inject it into the confirmation form.

The fix preserves the original intent—email links can still point to `/account/delete`—while ensuring that account deletion requires a valid CSRF token. An attacker cannot trick a victim into performing the deletion simply by embedding a link because the victim must actively submit the confirmation form, which includes the server-generated token that the attacker cannot obtain.

**Syntax verification:** Node.js `--check` passed on the fixed file.

## Behaviour changes

- **GET `/account/delete`**: Previously executed account deletion immediately. Now returns an HTML confirmation page. Users and scripts following old links will see a form instead of direct deletion.
- **POST `/account/delete`**: New endpoint. Handles the actual account deletion and requires a valid CSRF token in the `_csrf` body field.
- **Token generation:** The confirmation page now includes a server-generated CSRF token bound to the user's session. Tokens are single-use and expire with the session.
- **User experience:** Users clicking email confirmation links now land on a confirmation page where they must click "Delete My Account" to complete the action, rather than deletion happening silently on link click. This is the intended safe pattern when a state change must be triggered from an out-of-band channel.
