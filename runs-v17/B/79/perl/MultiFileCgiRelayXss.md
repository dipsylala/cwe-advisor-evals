## Verdict

**CONFIRMED** - CWE-79 (Improper Neutralization of Input During Web Page Generation)

The `subject` parameter, sourced from untrusted user input via `CGI::param()`, flows through `TicketSummary` to `TicketPageRenderer::render_confirmation()` where it is interpolated directly into HTML output without encoding. An attacker can inject XSS payloads (e.g., `<script>alert(1)</script>`) that execute in the victim's browser.

## Source

**File**: `ticket_controller.pl`, line 14  
**Entry point**: `$cgi->param('subject')` — untrusted user input from a CGI query parameter

**Data flow**:
1. User submits a ticket with `subject` parameter from the web form
2. `ticket_controller.pl:14` reads it: `my $subject = $cgi->param('subject');`
3. Passed to `TicketSummary->new(subject => $subject)` where it is stored unchanged (not validated)
4. Rendered via `TicketPageRenderer::render_confirmation()` at line 19 where it is interpolated directly into HTML

**Sink**: `TicketPageRenderer.pm`, line 19  
`say "<p>Subject: $subject</p>";` — direct string interpolation into HTML output

## Fix

### File: TicketPageRenderer.pm

```perl
package TicketPageRenderer;
# Renders the confirmation page shown to the requester after a ticket
# is filed, using the summary object assembled by TicketSummary.
use strict;
use warnings;
use feature 'say';
use HTML::Entities;

sub render_confirmation {
    my ($summary) = @_;

    my $ticket_id = $summary->ticket_id;
    my $priority  = $summary->priority;
    my $subject   = $summary->subject;

    say "<html><body>";
    say "<h1>Ticket #$ticket_id filed</h1>";
    say "<p>Priority: $priority</p>";
    say "<p>Subject: " . encode_entities($subject) . "</p>";
    say "</body></html>";

    return;
}

1;
```

## Explanation

The fix adds `use HTML::Entities;` and replaces the vulnerable interpolation of `$subject` with `encode_entities($subject)`. The `encode_entities()` function (with no second argument) encodes all HTML special characters including `<`, `>`, `&`, `"`, and `'` into their entity representations (`&lt;`, `&gt;`, `&amp;`, `&quot;`, `&#39;`). This transforms any injected markup into literal text that displays in the browser instead of executing.

The other variables (`$ticket_id` and `$priority`) remain unencoded because they are not user-controlled: `ticket_id` is generated by the application and `priority` is validated against a known allowlist in `_normalize_priority()`, making them safe to output directly.

The `say` function continues to work as before, printing the encoded output to STDOUT.

## Behaviour changes

**Input handling**: User-supplied subject text containing HTML characters (e.g., `50% off < $100`) now displays with encoded entities (`50% off &lt; $100`) instead of being interpreted as HTML. Legitimate special characters in subject text are now preserved as visible text in the confirmation page.

**Security**: XSS payloads such as `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`, or `' onclick='alert(1)` are now rendered as harmless text and cannot execute JavaScript in the victim's browser.

**Backward compatibility**: The output remains valid HTML. The encoding is transparent to end-users viewing legitimate subject text—encoded entities render as their intended characters in all browsers.
