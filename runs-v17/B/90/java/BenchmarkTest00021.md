## Verdict

Exploitable. The vulnerability is confirmed: untrusted user input from `request.getParameter()` is directly concatenated into an LDAP filter string without escaping, allowing an attacker to inject LDAP filter syntax and modify the search logic.

## Source

Line 44: `String param = request.getParameter("BenchmarkTest00021");` — attacker-controlled request parameter, treated as trusted and directly concatenated into the filter at line 54.

## Explanation

The fix replaces unsafe string concatenation with JNDI's parameterized filter API. Instead of building the LDAP filter by concatenating the untrusted `param` value directly into the filter string, the fix uses placeholder syntax (`{0}`, `{1}`) in the filter and passes user input via the `filterArgs` parameter array. JNDI automatically escapes each argument in `filterArgs` according to RFC 4515, neutralizing LDAP metacharacters (`*`, `(`, `)`, backslash, NUL) and preventing filter injection. The attacker-supplied value is treated as data, not filter syntax, so injection payloads like `*` or `)(uid=*)` are safely escaped and searched as literal strings. The sink `ctx.search(base, filter, filters, sc)` receives the escaping guarantee from the JDK's LDAP service provider.

## Behaviour changes

None. The parameterized filter API produces identical results to the vulnerable concatenation for legitimate inputs, but safely escapes special characters. The `ctx.search()` method signature remains unchanged (`search(name, filterExpr, filterArgs, controls)`), and the returned results enumerate identically. The only difference is that injection attacks now fail harmlessly because the LDAP filter syntax no longer interprets injected metacharacters.
