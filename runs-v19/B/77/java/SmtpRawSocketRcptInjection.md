## Fix

### File: SmtpRawSocketRcptInjection.java

```java
import jakarta.mail.Message;
import jakarta.mail.Session;
import jakarta.mail.Transport;
import jakarta.mail.internet.AddressException;
import jakarta.mail.internet.InternetAddress;
import jakarta.mail.internet.MimeMessage;
import javax.servlet.http.HttpServletRequest;
import java.util.Properties;

public class SmtpRawSocketRcptInjection {

    public void sendOrderConfirmation(HttpServletRequest request) throws Exception {
        String recipientAddress = request.getParameter("customerEmail");

        // Validate the recipient address
        InternetAddress validatedAddress;
        try {
            validatedAddress = new InternetAddress(recipientAddress, true);
        } catch (AddressException e) {
            throw new IllegalArgumentException("Invalid recipient address", e);
        }

        // Configure the SMTP session
        Properties props = new Properties();
        props.put("mail.smtp.host", "mail.internal.example.com");
        props.put("mail.smtp.port", "25");

        Session session = Session.getInstance(props);

        // Create and send the message using Jakarta Mail
        Message message = new MimeMessage(session);
        message.setFrom(new InternetAddress("no-reply@example.com"));
        message.setRecipients(Message.RecipientType.TO, new InternetAddress[]{validatedAddress});
        message.setSubject("Order confirmation");
        message.setText("Thanks for your order.");

        Transport.send(message);
    }
}
```

## Explanation

The vulnerability is closed by replacing raw SMTP command building with Jakarta Mail's structured `Transport.send()` API. The original code concatenated untrusted input directly into SMTP protocol commands, allowing injection of additional commands via embedded `\r\n` sequences (e.g., `attacker@evil.com\r\nRCPT TO:<target@victim.com>` would add an unauthorized recipient). The fixed code:

1. Validates the recipient address using `new InternetAddress(address, true)` in a try/catch block, rejecting malformed addresses as `AddressException`.
2. Uses only the validated `InternetAddress` object for all downstream sinks (the `setRecipients()` call), never the original untrusted string.
3. Replaces socket-based command composition with Jakarta Mail's `MimeMessage` and `Transport.send()`, which handles all SMTP protocol details and frames commands safely. This eliminates all points where untrusted input can be interpreted as SMTP metacharacters.

The fix requires the implementation artifact with CVE-2025-7962 fixes: `com.sun.mail:jakarta.mail` version 2.0.2 or later (or 1.6.8+ for the legacy line), OR `org.eclipse.angus:smtp` version 2.0.4+. Upgrading the API artifact alone (`jakarta.mail:jakarta.mail-api`) does not include the implementation fix.

## Behaviour changes

- **Signature change to exception contract:** The original method throws generic `Exception`; the fixed code now also throws `IllegalArgumentException` if address validation fails. Callers that catch `Exception` will handle this; callers with narrower exception handlers should be updated to catch or declare `IllegalArgumentException` separately if desired.
- **Configuration properties:** The fixed code now uses `Properties` to configure the Session instead of passing a raw socket. This is required to give Jakarta Mail the connection details. The host and port are now read from Properties, not hardcoded in the socket constructor.
- **SMTP command dialect shift:** Raw SMTP commands (`EHLO`, `MAIL FROM:`, `DATA`, `QUIT`) are no longer visible in the code; they are generated by Jakarta Mail. This is a semantic change that leaves the message content (from, to, subject, body) identical but trades direct command visibility for injection safety.
- **No socket returned to caller:** The original code managed a `Socket` directly; the fixed code returns nothing socket-related. If the caller expected to access the socket for any reason (logging, certificate inspection, etc.), that path is lost and would require a different approach (such as custom transport configuration with a `MailSessionFactory`).
- **Default session configuration:** `Session.getInstance(props)` uses a single shared session per properties set; the original code created a new socket per call. For multi-threaded use, this is safer. For single-use/one-off messages, this is semantically equivalent.
