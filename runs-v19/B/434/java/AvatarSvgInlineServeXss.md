## Verdict

Exploitable. SVG files uploaded through an allowlist-validated mechanism are served inline without `Content-Disposition: attachment`, allowing embedded JavaScript to execute in the browser. An attacker can upload a valid SVG with inline `<script>` tags or event handlers, and the JavaScript executes when another user views the avatar, leading to XSS.

## Source

`AvatarStorage.store()` receives bytes that have been validated against an allowlist of image types (image/png, image/jpeg, image/svg+xml). The method generates a random filename with the correct extension and stores the file. The upload validation is correct.

## Fix

### File: AvatarDownloadController.java

```java
package cases.upload;

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import org.springframework.http.HttpHeaders;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class AvatarDownloadController {
    private static final Path STORAGE_ROOT = Path.of("/var/app-data/avatars");

    @GetMapping("/api/avatars/{storedName}")
    public ResponseEntity<byte[]> download(@PathVariable String storedName) throws IOException {
        byte[] bytes = Files.readAllBytes(STORAGE_ROOT.resolve(storedName));
        String contentType = storedName.endsWith(".svg") ? "image/svg+xml" : "image/*";

        // Force attachment download to prevent inline rendering of SVG/HTML content that may contain scripts
        return ResponseEntity.ok()
            .header(HttpHeaders.CONTENT_TYPE, contentType)
            .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"" + storedName + "\"")
            .header("X-Content-Type-Options", "nosniff")
            .body(bytes);
    }
}
```

## Explanation

The vulnerability exists at the serving stage, not the upload stage. Although the upload correctly validates file type and generates a random filename, the download endpoint serves SVG files with `Content-Type: image/svg+xml` without `Content-Disposition: attachment`. This causes browsers to render SVG inline, where embedded `<script>` tags or event handlers execute as JavaScript in the user's context, enabling XSS.

The fix adds two headers: `Content-Disposition: attachment` forces the browser to download the file rather than render it inline, preventing JavaScript execution. `X-Content-Type-Options: nosniff` prevents the browser from MIME-type sniffing, which adds defense-in-depth. The fix uses the already-stored filename in the disposition header, which is safe because that filename was generated by the server (UUID-based) and is not client-supplied.

## Behaviour changes

1. **Content-Disposition header added** - Reason: Forces browser to download files rather than render inline, blocking XSS. This is a safety change necessary to fix the weakness.

2. **X-Content-Type-Options header added** - Reason: Prevents MIME type sniffing attacks. This is a hardening measure recommended by the CWE-434 guidance.

3. **Return chain modified** - Reason: The ResponseEntity is constructed using a fluent builder chain instead of a single return statement. No functional change; readability improvement to accommodate multiple headers. The response still returns the same bytes with the same Content-Type.

No other behavior changes. The method still returns the file bytes, still resolves the path correctly, and still determines the content type by checking the stored extension.
